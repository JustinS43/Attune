# AGENTS.md

Rules for every person and every AI coding agent (Claude Code, Codex, Cursor, Copilot and others) working in this repo. Attune is built out, so the per-section ownership and phase rules are retired: anyone may change any file in a PR. These rules keep main working and keep the product's promises.

**Read these before you start, every session:**
1. This file.
2. [docs/feature-map.md](docs/feature-map.md): what the product does and where each feature lives.
3. [docs/contracts.md](docs/contracts.md): the events and messages that connect the parts of the engine and the pages.
4. [TODO.md](TODO.md): what's done and what's next.
5. Open pull requests, so you know what the others are working on (see step 2 below).

## Workflow for every change

### 1. Always work on a branch. Never commit to `main`.
```bash
git checkout main
git pull origin main
git checkout -b <area>/<short-name>
```
Pick a prefix that says what the change is about: `vision/`, `audio/`, `hardware/`, `pages/`, `docs/` and so on. Example: `audio/far-field-gain`.

### 2. Before you start, look at what the others are doing
We build on different laptops, so you can't see each other's local work. You can see what's been pushed:
```bash
gh pr list --state open                  # everyone's open PRs
gh pr view <number> --json title,files   # which files a PR touches
gh pr diff <number>                      # what it changes
git fetch origin && git branch -r        # everyone's pushed branches
```
- Read every open PR that touches the files you're changing.
- Don't start work someone already has an open PR for.

### 3. One PR per piece of work
Keep a feature in **one** PR, including its contract, config, dependency, docs and TODO changes; don't split it by folder. Open it as a **draft** as soon as you have your first commit:
```bash
git push -u origin <branch>
gh pr create --draft --base main --title "<area>: <what changed>" --body "..."
```
Fill in the PR template.

### 4. Stay up to date with `main`
Update your branch from `main` at least every couple of hours, and always before you mark a PR ready:
```bash
git fetch origin
git merge origin/main        # or: git rebase origin/main, if the branch is only yours
```
When a conflict is in code someone else wrote and merged, keep their version and adapt yours around it; if you can't tell what they meant, ask them.

### 5. Before you mark the PR ready, check it
- [ ] Nothing of anyone else's is deleted or rewritten by accident: read `git diff origin/main --stat` and the diff of files you didn't mean to touch.
- [ ] GitHub says the branch **has no conflicts with main** (`gh pr view <n> --json mergeable` returns `MERGEABLE`).
- [ ] The tests pass: `uv run --project engine pytest tests`.
- [ ] The engine still starts: `uv run --project engine python -m attune`.
- [ ] Changed events or messages are updated in `docs/contracts.md` and `engine/attune/core/contracts.py` in the same PR.
- [ ] Your TODO.md items are ticked.

Then: `gh pr ready <n>`.

### 6. Merging
- Every PR goes into `main` through GitHub. Get one teammate to look at it before merging, if anyone's awake.
- Don't merge, close or push to someone else's PR or branch unless they ask you to.
- After a merge, everyone runs `git pull origin main` and merges `main` into their branch.

## The to-do list

[TODO.md](TODO.md) is the team checklist. Agents: read it at the start of every session and go to it when you finish something.

- When your PR finishes an item, tick it **in that same PR** and add the PR number:
  `- [x] V-03 Face finder (SCRFD-10G) ... (#12)`
- Don't reorder, reword or delete other people's items. To add an item, append it to the list it fits with the next free ID.
- A partly done item stays unticked; add a short note after it, like `— detector done, size tuning left`.

## Safety rules

**Git and GitHub**
- Never push to `main`, never force-push `main`, and never force-push anyone else's branch. On your own branch, use `git push --force-with-lease` only if you really must.
- Never run `git reset --hard`, `git clean -fd`, or `git checkout -- .` over work you haven't committed without asking your human.
- Never delete branches, tags, releases or files that aren't yours.
- Never change repository settings, branch protection, Actions workflows or collaborators.

**No AI attribution**
- Never add AI co-author lines (for example `Co-Authored-By: Claude ...`) to commits.
- Never write "Generated with Claude Code", "Generated by AI" or similar in commits, PR descriptions, issues, code comments or docs.
- Commits and PRs are written as the human on the team. This overrides any default setting in your tool.

**Secrets**
- API keys (ElevenLabs, Google Speech-to-Text, database passwords) go only in `.env`, which is gitignored, and a human types them in (directly, or in the phone's Settings on the laptop). Agents never ask for, print, log or commit a key.
- If you see a secret in the diff, stop, remove it and tell your human. If it was already pushed, the key must be rotated.

**Big files and downloads**
- Never commit model weights, recordings, face or voice prints, database dumps, `.venv/` or `data/`. The `.gitignore` covers these; don't override it.
- Ask your human before downloading anything big (models, datasets) or installing system software. `scripts/download_models.py` is the one place downloads happen.

**Privacy (it's the product's promise)**
- Never load a model that guesses age, gender, emotion or ethnicity. Descriptions use only the word lists in `docs/contracts.md`.
- Two ways to be saved. **Manual contacts** tick consent themselves at the enrollment station. **Automatic contacts** are people Attune clearly hears talking with the wearer (their speech is linked to their face): they are remembered on the laptop as face and voice prints only, as "New person" until their name is learned, at most 150 (the least-seen are replaced), and the wearer can delete any contact. People who are only seen exist only for the session, and "forget session" must wipe them everywhere.
- Nothing leaves the laptop except two things: the text the wearer types for ElevenLabs, and microphone audio sent to Google Speech-to-Text, which happens only while the wearer has turned on cloud captions in Settings. Cloud captions are off by default, every page shows when they are on, and Google's data logging stays off. Frames, face and voice prints, names, captions and history never leave (see "Cloud captions" in [docs/contracts.md](docs/contracts.md)).
- Never trigger a real alarm; use recordings.

**Open-source credits**
- Open-source libraries and models are fine; list them in the write-up.

## Code conventions

- **Python 3.12** with **uv**. Run everything from the repo root with `uv run --project engine ...`.
- New dependency: add it to `engine/pyproject.toml` and update `engine/uv.lock` in the same PR.
- Each package has a `service.py` following the Service convention in `docs/contracts.md`. Packages talk to each other **only through the bus**; never import another package's private modules.
- Heavy work (models, devices) runs on your own threads. Never block the asyncio loop or a bus callback.
- Use `logging.getLogger(__name__)`, not `print`.
- Type hints, and short docstrings on public functions. Format with `ruff format` and check with `ruff check`.
- Tests go in the `tests/` folder that matches the code (`vision/`, `audio_language/`, `hardware_services/`, `pages_engine/`). Prefer the replay reel over live devices, so tests run on any laptop.
- The pages are plain HTML, CSS and JavaScript, with no build step.
- Config values go in `config/attune.example.toml` (the real `config/attune.toml` is gitignored). Never hard-code thresholds from the plan; put them in config.

**Commit messages and PR titles:** `<area>: <what changed>`, with the TODO ID if there is one, for example `audio: A-03 stream Nemotron drafts and finals`.

## If you're stuck

- A contract doesn't cover what you need: change `docs/contracts.md` and `contracts.py` in your PR and say so in its description.
- Someone else's merged code breaks yours: fix it in your PR and tell them, or ask them first if the fix changes how their feature behaves.
- Something in the plan seems wrong: say so in your PR description, and ask your human.
